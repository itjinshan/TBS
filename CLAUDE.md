# TBS (Travel Buddy Service)

A MERN-stack travel-planning app: a React SPA frontend backed by an Express/MongoDB API. TBS is the consumer ("project-A") of the separate **DS-Service** backend, which it calls for LLM-backed trip planning and (eventually) destination/spot data.

@../DS-Service/CLAUDE.md

> **DS-Service is the upstream data source — check its API contract (linked above, under "## API Contract") before creating DB models or making API calls to it.** Field-name casing, response shapes, and auth requirements there are authoritative; don't guess or re-derive them from TBS's own conventions.

This repo has two independent Node projects, each with its own `package.json`/`node_modules` — always `cd` into the relevant one before running scripts.

## `Node/` — Express API backend

Tech: Express, Mongoose, Passport (JWT strategy), bcryptjs, nodemailer, axios (for calling DS-Service).

**Commands** (run from `TBS/Node/`):
- `npm run dev` — `nodemon index.js` (auto-restart dev server)
- `npm start` — `node index.js` (no reload)
- No test script is defined.

**Structure:**
- `index.js` — app entry: Mongo connection, middleware, route mounting on port `process.env.PORT` (default 6666).
- `APIs/` — route modules: `auth.js` (register/login/current-user/password reset), `dsservice.js` (proxies to DS-Service), `token.js`, `trip.js` (trip intake, itinerary generation, CRUD on trips).
- `Config/` — `jwtgenerator.js` (mints access/refresh/DS-Service tokens), `passport.js` (JWT strategy setup).
- `DB_Models/` — Mongoose schemas: `DB_User.js`, `DB_Trip.js`.
- `Emails/` — nodemailer templates (welcome, confirmation, forgot/create password).
- `Services/spotSourcing.js` — real spot sourcing via DS-Service's `POST /datasourcing/sourcespots`; reshapes DS-Service's `SpotName`/unpopulated `City` ObjectId to the `Name`/destination-string shape TBS's schema and frontend expect.
- `Services/itineraryPlanner.js` — arranges a flat spot list into `duration` days via geographic clustering (greedy nearest-neighbor tour anchored to the accommodation or the spot centroid), not a naive ordered slice. Exports `SPOTS_PER_DAY` as the single source of truth for how many spots a trip's day-count should target.
- `Services/nluExtraction.js` / `Services/ruleBasedExtraction.js` — real LLM-based field extraction via DS-Service's `POST /nlu/extract` (destination/duration/travelers/budget/yes-no), falling back internally to the original regex-based extraction (`ruleBasedExtraction.js`) on any failure.
- `Services/fallbackItinerary.js` — fallback-only itinerary generator (formerly `mockItinerary.js`), used by `/trip/generate` only when the real spot-sourcing path fails outright (DS-Service network/HTTP error, or zero spots returned).
- `Services/amapPlaces.js` — real place lookup against Amap's Web Service "place text search" API (`searchPlaces(query, city)`), used by `/trip/intake`'s accommodation-confirm stage. Requires `AMAP_WEB_SERVICE_KEY` — falls back to a single unverified candidate if unset or if the call fails.
- `Validation/` — plain-function request-body validators (`login.js`, `register.js`, `resetPassword.js`, `isEmpty.js`).

**Conventions:**
- Route handlers use `.then()/.catch()` (not async/await) throughout `APIs/auth.js` and `APIs/trip.js`.
- DB model fields are PascalCase (`FirstName`, `Email`, `ResetToken`), matching DS-Service's convention — keep new fields consistent with this casing.
- User-facing auth routes issue tokens via `generateAccessToken(user, 'auth' | 'refresh' | 'deepseek')` in `Config/jwtgenerator.js`. The `'deepseek'` usage is what signs the `token` field DS-Service expects (60s expiry, secret `DEEPSEEK_JWT_SECRET` — must match DS-Service's copy of the same secret).
- Calls into DS-Service go through `axios` with the base URL `process.env.DS_SERVICE_BASEURL`; see `APIs/dsservice.js` for the current pattern (mint a `'deepseek'` token, attach it as `token` in the JSON body — not a header — then POST).

**Env vars** (`Node/.env`): `PORT`, `MONGODB_URL`, `ACCESSSECRETE`, `REFRESHSECRETE`, `RESETSECRET`, `EMAIL_VERIFY_SECRET` (signs the 24h email-verification JWT minted on register, see `APIs/auth.js`), `DEEPSEEK_JWT_SECRET`, `GD_MAP_JWT_SECRET`, `AMAP_WEB_SERVICE_KEY` (Amap Web service key for `Services/amapPlaces.js` — distinct from `GD_MAP_JWT_SECRET` and from the JS API key `useAmap.js` loads client-side), `DS_SERVICE_BASEURL`, `EMAIL`/`EMAILPASS` (nodemailer SendinBlue credentials used by `Emails/verifyEmail.js`, `welcomeEmail.js`, `forgotPasswordEmail.js`).

## `react-frontend/` — React SPA

Tech: React 19, Redux Toolkit + Redux Thunk, React Router v6, MUI + Emotion, axios.

**Commands** (run from `TBS/react-frontend/`):
- `npm start` — dev server (`react-scripts start`), proxies API calls to `http://localhost:6666` (see `"proxy"` in `package.json` — i.e. the `Node/` backend above, not DS-Service directly)
- `npm run build` — production build
- `npm test` — CRA/Jest test runner (`react-scripts test`)

**Structure:** standard Create React App layout — `src/actions`, `src/reducers`, `src/components`, `src/hooks`, `src/utils`, `src/store.js` (Redux store setup), `src/App.js`.

**Conventions:** the frontend never talks to DS-Service directly — it goes through the `Node/` backend (`/dsservice/*`, `/trip/*` routes), which in turn calls DS-Service. If you're adding a UI feature that needs DS-Service data, the new/changed logic belongs in `Node/APIs/dsservice.js` (or a new route module) first, following DS-Service's contract, then wired up to the frontend through the existing proxy.

**Design for a future mobile app.** There's no mobile app in development right now, but one is planned, so keep that in mind on every UI decision here — even though today's target is web only. Concretely: avoid layout/interaction patterns that only make sense on a wide desktop viewport and would need a full rework for a native-sized screen (e.g. fixed pixel widths instead of relative/responsive sizing, hover-only interactions with no tap equivalent, multi-column layouts with no real mobile fallback). This isn't a mandate to build responsive/mobile-first *now* — it's a bias to apply when there's a reasonably low-cost choice between a web-only pattern and one that would translate more easily later.

### Bugs

Actual defects — existing behavior is wrong, not just missing. Prioritized ahead of the feature backlog below.

- **A concrete but non-transliterated English arrival/departure-point answer can fuzzy-match to a wrong-category real place, with no category check or confirm step to catch it.** Answering "where will you be arriving into the destination from" with "Shanghai Pudong Airport" resolved to **上海浦东香格里拉 (Shanghai Pudong Shangri-La — a hotel)**, not 上海浦东国际机场 (the actual airport). Root cause: `resolvePlacePoint()` (`APIs/trip.js`) passes the raw English query straight to `Services/amapPlaces.js`'s `searchPlaces()`, which is Amap's Chinese-text-first place-text-search — "Shanghai Pudong Airport" is a *translation*, not a transliteration, so it has near-zero token overlap with the airport's real Chinese name, and Amap's fuzzy matching instead ranked a hotel first (its record apparently has "Shanghai"/"Pudong" in a Latin-alphabet alt-name field). `resolvePlacePoint()` then takes `candidates[0]` unconditionally — no POI-type/category filter (Amap's results carry a type code that could distinguish "transit hub" from "hotel"), and no confirm-with-traveler step (intentionally skipped today per the function's own comment, "lower stakes than picking a hotel... top match... good enough"). **Distinct from the already-fixed "same airport" bug** (`isSamePlaceAnswer()`, see the resolved "Resolve 'same as arrival' departure answers without a fresh Amap search" commit) — that fix only short-circuits *vague/referential* answers ("same", "same airport") before they ever reach Amap; this case is a concrete, well-formed place name that still reaches Amap and gets confidently mismatched, so that existing fix doesn't cover it.
  - Possible fixes, not mutually exclusive: (1) proactively translate arrival/departure queries to Chinese before searching (mirrors `Services/spotPhotos.js`'s `translateToChineseName()`, but that fallback only fires on *empty* results — this query wasn't empty, just wrong, so arrival/departure resolution would need to translate every time, not just as an empty-result fallback); (2) filter or rank Amap candidates by POI type (e.g. prefer airport/station-type POIs when the query text suggests one) instead of blindly taking `candidates[0]`; (3) reintroduce a lightweight confirm step for arrival/departure ("Did you mean 上海浦东国际机场?") rather than silently trusting the top match.
  - Related to a planned move to conduct intake in Chinese for the China-first launch — doing so would likely reduce how often this specific failure mode (translated-not-transliterated English queries) occurs, since the root cause is an English query hitting a Chinese-text-first matcher. It would not fully close the gap on its own: a Chinese query can still rank a wrong-category POI first without a type filter or confirm step.

### Backlog

Backlog items surfaced while working on other plans, deliberately kept out of the active plan's PR scope. Pick these up as their own future PRs.

- **Multiple photos per spot, with arrow-key/click navigation through them.** Each spot card on the Itinerary page shows exactly one photo (`spot.Photo`), sourced by `Services/spotPhotos.js`'s `findSpotPhoto()`, which takes only `photos[0]` — the first image in Amap's POI photo album for whichever place the text search matched — with no relevance filtering. Surfaced by a bad real-world case: for "Beijing Olympic Park," the first photo returned was an unrelated close-up of a random booth/stall, not the park itself. Two related pieces of work: (1) have `searchAmapPhoto()` keep more than one photo per spot (Amap's POI response already includes a `photos` array, only `[0]` is used today) so a bad first pick isn't the only option shown; (2) add prev/next arrow-key (and click) navigation on the spot card so a traveler can page through a spot's photos instead of being stuck with whichever one happens to be first — needs `DestinationSpot`/`DB_Trip.js`'s `SpotSchema` to carry a `Photos` array instead of a single `Photo` string, plus a small carousel/gallery component on the card. Doesn't fix Amap's underlying match-quality issue (a bad top photo can still be first in the list) — multiple photos plus manual navigation is a mitigation, giving the traveler an escape hatch, not a guarantee every photo is representative.
- **Show each spot's map badge color in the Itinerary list too, not just on the map.** Now that the map has per-day colored/numbered marker badges (`components/itinerary/dayColors.js`'s `dayColor()`), the list has no visual link back to them — a traveler can't tell which list card corresponds to which map pin without reading names. Checked Wanderlog's actual list treatment (not just marketing copy — inspected a live trip plan) for reference: no tinted card backgrounds, no colored day-header — each list item instead gets the exact same small colored pin-shaped badge (color + visit-order number) as its marker on the map, placed next to the spot's title. Recommend the same approach for TBS: render the existing `dayColor(dayNumber)` badge markup (already built for `updateMarkers()` in `Itinerary.js`) inline at the front of each spot card too, sized down for list use — reuses the already-validated palette/contrast as-is, no new color derivation (a light/transparent tint version would need its own contrast check against card text; this doesn't). Arrival/accommodation/departure list rows, if ever shown as list rows the way spots are, would keep their emoji-icon treatment rather than a color badge, matching the map's existing WAYPOINT_ICONS split.
- **Per-spot "similar attractions" carousel with expand-to-swap.** Under each spot card in the Itinerary list, always show a horizontally-scrollable row of 3 candidate alternative spots (small card: 1 photo + name each) from the same city's already-sourced spot pool. Modeled on Wanderlog's "Recommended places" row (small photo+name cards, horizontal scroll — confirmed live), with one deliberate difference: Wanderlog's version sits once at the end of the whole "Places to visit" list and only *adds* a new place; this attaches the same card pattern to each individual spot instead, for *swapping* that one spot.
  - **Candidate selection — generalizes the existing single-pick swap, doesn't duplicate it.** Extend `itineraryPlanner.js`'s `findReplacementSpot()` into a `findReplacementSpots(destination, usedNamesLower, currentSpot, topN)`: (1) **gate** candidates by time-consumption compatibility against the spot being replaced (`AverageTimeSpent` within a tolerance band of the original — proposed starting point ±40%, needs a real number picked during implementation) — a candidate whose visit time is wildly different breaks the day's time budget (`splitIntoDays`'s `activeBudgetMinutes`) regardless of how well it otherwise scores; (2) **score** the survivors out of 10 — 4 points for `Rating` (normalized), 3 for matching `Category`, 3 for geographic closeness to the spot being replaced (haversine, normalized against a search radius); (3) return the top `topN`, excluding anything already used anywhere in the itinerary (existing behavior, kept). The existing chat-based swap (`replaceSpotInDay`) becomes `topN=1` through this same function, so both entry points share one ranking instead of drifting apart. Fetch each city's spot pool once per itinerary load (already DB-cached via `sourceSpotsForCity`) and rank per-spot in memory — not a fresh sourcing call per spot per card, which "always visible under every spot" would otherwise multiply badly (7-14+ spots per trip).
  - **UI:** clicking one of the 3 small cards opens its detail in the map-side panel, not inline in the list — matches Wanderlog's own pattern (confirmed live) and keeps the list itself from getting congested with expanded cards stacking up between spots. `Itinerary.js` already has a right-hand map column (`AccommodationMap`-style panel/InfoWindow patterns already exist there for marker clicks); this reuses that same panel real estate for a candidate's detail view — worthiness rating, time consumption, and multiple scrollable photos (depends on the multi-photo/arrow-key-navigation item above landing first, since it reuses that same gallery component) — rather than opening a new UI surface. A "Swap" button in the detail panel replaces the original spot (the one this carousel is attached to) via the shared swap function above — same `POST /trip/refine` swap flow as today's chat-based swap, just a new, more discoverable UI entry point onto it.
- **Drag-and-drop reordering of spot cards in the Itinerary list.** Each day's spot cards (`components/itinerary/Itinerary.js`) are static — no way to reorder spots within a day, or move a spot to a different day, without going through the refine chat's swap flow (which only replaces, not reorders/moves). Wanderlog supports exactly this (drag a card within its day's list to reorder, or into another day's list to move it) — reference that for the interaction model. Needs: a drag-and-drop library (for React 19, `@dnd-kit` over the older, now-unmaintained `react-beautiful-dnd`), an itinerary mutation for both cases (in-day reorder is a simple splice; cross-day move touches both the origin and destination day's `Spots` array), and `buildRoute()` recomputed for every day touched (both, on a cross-day move) so the map/route stay in sync — same recompute `replaceSpotInDay` already does for a swap, just triggered by drag-drop instead of chat. - **Network-reachability-based provider routing — confirmed to affect the map widget itself, not just POI search quality.** Surfaced while testing the Amap place lookup used for the has-a-place accommodation flow: Amap's POI data/keyword matching is unreliable outside mainland China (English-language searches for well-known hotels in Paris/Tokyo returned irrelevant results even with correct city scoping). Confirmed in later testing that this is more than a search-quality issue: Amap's *base map tiles* themselves don't render for non-China destinations at all — the accommodation-candidate map and the Itinerary page's map (`components/itinerary/Itinerary.js`) both show a blank grid with only the markers visible (no roads, no labels, no imagery) for e.g. Ghent or Prague, while the same map instance renders full detail instantly for a China location (confirmed by the geolocation-recenter bug above accidentally landing the viewport in Kunming). Consistent across multiple destinations and load waits well beyond normal tile-load latency, so this reads as a genuine coverage gap in Amap's tiles outside China, not a slow-render issue. The routing needed here is two separate axes, not one "China vs. not" switch:
  - **User's network/region is the reachability gate, not a quality preference.** Google's services (Maps included) are blocked at the network level inside mainland China, so a China-network user planning a *non-China* trip still can't be routed to Google Maps — it simply won't load for them, regardless of match quality. Likewise ChatGPT/OpenAI's API is generally unreachable from mainland China. So:
    - **China network** → Amap (+ DS-Service `ds: 'deepseek'`) for **every** destination, for now — not because Amap is a good fit for e.g. a Tokyo search, but because it's the only reachable option. This is an accepted limitation, not a bug, until there's a real fix for the geofencing (e.g. a server-side proxy that calls Google Places from outside China on the user's behalf, so the client never talks to Google directly — worth designing later, not part of this item).
    - **Non-China network** → both Amap and Google Maps are reachable, so **destination-based** routing can apply within this group: Amap for China destinations (best data there), a new `Services/googlePlaces.js` (not yet built) + DS-Service `ds: 'chatgpt'` for non-China destinations (already scaffolded as a `501` stub in `POST /datasourcing/sourcespots` — see DS-Service's `CLAUDE.md` — but not yet implemented).
  - **Check Amap's own "World Map" (世界地图) feature before building a second map provider.** Amap JS API 2.0 has an official overseas coverage mode — `showOversea: true` at map init, claiming 200+ countries/regions with "detailed road data and POI" outside China — which, if it actually delivers usable quality for e.g. Ghent/Prague, would fix this with **zero new integration**: same SDK, same key architecture (`REACT_APP_AMAP_KEY`/`REACT_APP_AMAP_SECURITY_JS_CODE`/`AMAP_WEB_SERVICE_KEY` already in place), reachable from China same as today — potentially closing *both* the non-China-network and the harder China-network+non-China-destination case at once, without a second map provider or the server-side-proxy workaround below. **Do this check first** — it changes the shape of everything below if it works.
    - **Application process:** gated behind a separate commercial approval, not a self-serve flag — requires filing a work-order ticket through Amap's developer console requesting "商务咨询" (business consultation). Needs whoever holds TBS's Amap developer account to actually file it; not something that can be done without that access.
    - **Pricing:** not published anywhere for World Map specifically — only available via that same sales conversation. For context, Amap's general commercial API "Technical Service License" (likely a prerequisite tier, separate from World Map itself) runs ¥50,000/year (Basic) to ¥100,000/year (Premium) — TBS's current Amap keys look like the free/dev tier per the env var docs above, so this would likely mean a paid-tier move at minimum, not just a feature unlock.
    - **Positioning:** a 2025 Amap press release upgrading World Map (300M+ POI, multi-modal navigation) explicitly lists "online travel platforms" as a target customer segment alongside logistics/delivery/ride-hailing — directly relevant to TBS, and a signal it's an actively maintained enterprise product, not an afterthought, but priced/gated accordingly.
    - Sources: [World Map guide](https://lbs.amap.com/api/javascript-api-v2/guide/map/world-map), [World Map solution page](https://lbs.amap.com/solution/abroad), [Amap service/pricing page](https://lbs.amap.com/upgrade), [Amap World Map upgrade press release](https://www.prnewswire.com/news-releases/amap-platform-upgrades-world-map-service-with-multi-modal-navigation-and-300m-poi-302819384.html), [Zhihu discussion of Amap/Tencent/Baidu commercial licensing fees](https://www.zhihu.com/question/484885366).
  - **If World Map isn't viable (denied, too costly, or overseas quality turns out poor in testing), fall back to routing the map widget itself, not just the search API behind it.** For non-China-network users viewing a non-China destination, swap the actual map instance — a new `useGoogleMap` hook alongside the existing `useAmap` (`hooks/useAmap.js`), with `Itinerary.js` and the accommodation-candidate map choosing between them by the same reachability+destination logic, over a shared provider-agnostic marker shape so both map components don't need separate rewrites. For China-network users viewing a non-China destination, there's no equivalent swap available (Google is unreachable), so this stays the accepted limitation above until the geofencing workaround exists.
  - **Cheap interim mitigation, worth doing regardless of which fix above lands:** detect the no-tiles case and show something more honest than a blank grid (e.g. a "map preview unavailable for this destination" notice with the marker list still usable), rather than a map that just looks broken.
  - **Query-language translation follows whichever provider is active, not the user's own language.** Translating the query to Chinese is what actually fixed Amap's match quality in testing — that holds whenever Amap is in use, whether it was chosen because the destination is in China or because the user's network left no other option. No translation is expected to be needed for Google Maps queries (handles multi-language input more gracefully).
  - **UI language and LLM-backend selection are a separate, user-scoped concern**, independent of the above: default UI language from IP region (China IP → Chinese default, overridable via the language switcher — `react-i18next` + `components/layout/LanguageSwitcher.js` now built, currently defaulting to browser language rather than true IP-region detection), and LLM backend follows the same network-reachability gate as the maps provider (China network → Deepseek, regardless of destination).
  - Scope for the eventual PR: land the network-based reachability gate and the destination-based refinement within the non-China group. The non-China Google Maps/ChatGPT build-out and the China-network geofencing workaround are both separate follow-ups, not part of this either.
- **User feedback on spots and itineraries.** A simple rating mechanism — after visiting a spot, and after completing a trip — for the traveler to rate their real experience. Purpose: today's `Rating` field on every spot is entirely an LLM guess (see `DS-Service/CLAUDE.md`'s "How Spot Sourcing Works"); real user ratings, accumulated across the user base, are a first-party, fully-owned data source that could eventually supplement or replace the LLM-guessed rating with something grounded in actual visitor experience. Needs: a new TBS-side rating endpoint/UI (likely on the Itinerary page or a post-trip prompt), a place to store per-user per-spot/per-trip ratings (a new Mongoose collection, since `DestinationSpot` lives in DS-Service's database, not TBS's — the aggregation/rollup of user ratings back into DS-Service's spot data is a separate design question, not just a UI addition), and a decision on how (or whether) aggregated user ratings get blended with or replace the LLM's `Rating` value on each `DestinationSpot`.
- **Let travelers name specific must-visit spots during intake, with a search-and-pick-card flow instead of chat back-and-forth.** Most travelers already have specific places in mind before they start planning. Add a new intake question (`STAGES` in `APIs/trip.js`, placed near `DESTINATION`) asking whether the traveler has particular places they want to visit; if yes, switch to a dedicated input box (not a chat message) where each name they type triggers a place search (reuses `Services/amapPlaces.js`'s `searchPlaces()`, the same lookup `ACCOMMODATION_CONFIRM` already uses) and shows the results as small cards (photo, name, address, a `+` button) — since a name search can match more than one real place, the cards let the traveler pick the exact one they meant rather than trusting a single auto-matched guess. Repeatable (type another name, get another set of cards) until they're done adding. Once finished, itinerary generation needs to treat these as forced-include spots layered on top of the existing LLM-sourced pool — `itineraryPlanner.js`'s `buildGreedyTour`/`splitIntoDays` would need these spots guaranteed a place in the schedule, not just competing on `Rating` like the rest of the pool the way replacement candidates do. Open question worth deciding during implementation: what happens if the traveler names more must-visit spots than the trip's `duration` can reasonably fit — silently trim to the highest-priority/best-fitting subset, or surface it back to the traveler (e.g. "that's a lot for 3 days — want to add a day, or should we fit as many as we can")?

  - **What gets cached, and how:** don't build a dedicated generation pipeline for this — opportunistically cache a real trip as it's naturally generated (in testing or by real users) whenever it matches (1) a recognized popular city (a small, growable list — e.g. Beijing, Shanghai, New York — not hardcoded to be exhaustive) and (2) one fixed "showcase" preference profile: mid-range budget, standard pace, 2 travelers, public transit. First matching trip generated for a city gets cached; not overwritten after that (no manual curation step for now). Needs a new small collection (distinct from per-user `Trips`, since this is city-keyed and publicly readable without auth) storing the day-by-day plan plus a reference back to the source `Trip` for traceability. **Leave room to upgrade "first match wins" to "highest-rated match wins" later**, once the "User feedback on spots and itineraries" item above lands — schema this so that's a query change, not a rewrite.
  - **Personal fields don't carry over.** `arrivalPoint`/`departurePoint`/`accommodation` are specific to whoever generated the original cached trip and won't apply to a new anonymous visitor — strip them from what's cached/shown; the days/spots themselves are what's being showcased. They stay blank on the landed Itinerary page until the visitor's own refine-chat conversation fills them in.

The refine chat (`POST /trip/refine`) still opens, but its first message changes from today's "Want to change anything about this plan? - **Offer similar-hotel suggestions when the traveler has a place "in mind" but hasn't booked it.** `STAGES.ACCOMMODATION_CHOICE` (`APIs/trip.js`) asks one bundled yes/no question — "do you already have a place booked or in mind?" — and treats a "yes" identically either way: `searchAndPresent()` looks up the named place and only ever asks the traveler to confirm that exact match (`STAGES.ACCOMMODATION_CONFIRM`). That's the right flow for an already-booked place, but if the traveler only has one *in mind* (not booked), they'd likely also want to see similar alternatives — the same kind of listing `suggestAccommodations()` already produces for the no-place path — rather than a single confirm-or-search-again loop. Needs distinguishing the two cases at the `ACCOMMODATION_CHOICE` stage (a third yes/no-style option, or a follow-up question) and, for the "in mind" case, extending the confirm flow to also offer nearby/similar options. Deliberately not part of the current accommodation-suggestion format work — logged as its own future item.
- **After accommodation is settled, help find flights/train tickets — but only if the traveler doesn't already have their own transportation sorted.** Continues the same post-generation conversation as the now-built accommodation-settling flow (`POST /trip/refine`'s `REFINE_STAGES.PICK_ACCOMMODATION` → `EDITING` transition), one step further: once accommodation is settled, check whether the traveler already has a flight or train booked for their `arrivalPoint`/`departurePoint`. Otherwise, don't ask about it any earlier in the flow (during intake or itinerary-review) — set it aside and come back to it only as the next step after accommodation, then help find the cheapest available ticket for the traveler's preferred travel dates. Needs a flight/train ticket-search integration (provider not yet decided) — the persistent Itinerary-page chatbot this depends on already exists, so this item is otherwise unblocked.
- **Caching layer for volatile external lookups (e.g. Redis).** Decided against storing a raw price field on the `Accommodation` sub-document (`DB_Trip.js`) since pricing is date/availability-dependent and goes stale almost immediately — it should be fetched live at suggestion/generation time, not persisted in Mongo.
