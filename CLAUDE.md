# TBS (Travel Buddy Service)

A MERN-stack travel-planning app: a React SPA frontend backed by an Express/MongoDB API. TBS is the consumer ("project-A") of the separate **DS-Service** backend, which it calls for LLM-backed trip planning and (eventually) destination/spot data.

@../DS-Service/CLAUDE.md

> **DS-Service is the upstream data source — check its API contract (linked above, under "## API Contract") before creating DB models or making API calls to it.** Field-name casing, response shapes, and auth requirements there are authoritative; don't guess or re-derive them from TBS's own conventions.

This repo has two independent Node projects, each with its own `package.json`/`node_modules` — always `cd` into the relevant one before running scripts.

## `Node/` — Express API backend

Tech: Express, Mongoose, Passport (JWT strategy), bcryptjs, nodemailer, axios (for calling DS-Service).

**Commands** (run from `TBS/Node/`):
- `npm run dev` — `nodemon index.js` (auto-restart dev server)
- `npm start` — `node index.js` (no reload)
- No test script is defined.

**Structure:**
- `index.js` — app entry: Mongo connection, middleware, route mounting on port `process.env.PORT` (default 6666).
- `APIs/` — route modules: `auth.js` (register/login/current-user/password reset), `dsservice.js` (proxies to DS-Service), `token.js`, `trip.js` (trip intake, itinerary generation, CRUD on trips).
- `Config/` — `jwtgenerator.js` (mints access/refresh/DS-Service tokens), `passport.js` (JWT strategy setup).
- `DB_Models/` — Mongoose schemas: `DB_User.js`, `DB_Trip.js`.
- `Emails/` — nodemailer templates (welcome, confirmation, forgot/create password).
- `Services/spotSourcing.js` — real spot sourcing via DS-Service's `POST /datasourcing/sourcespots`; reshapes DS-Service's `SpotName`/unpopulated `City` ObjectId to the `Name`/destination-string shape TBS's schema and frontend expect.
- `Services/itineraryPlanner.js` — arranges a flat spot list into `duration` days via geographic clustering (greedy nearest-neighbor tour anchored to the accommodation or the spot centroid), not a naive ordered slice. Exports `SPOTS_PER_DAY` as the single source of truth for how many spots a trip's day-count should target.
- `Services/nluExtraction.js` / `Services/ruleBasedExtraction.js` — real LLM-based field extraction via DS-Service's `POST /nlu/extract` (destination/duration/travelers/budget/yes-no), falling back internally to the original regex-based extraction (`ruleBasedExtraction.js`) on any failure.
- `Services/fallbackItinerary.js` — fallback-only itinerary generator (formerly `mockItinerary.js`), used by `/trip/generate` only when the real spot-sourcing path fails outright (DS-Service network/HTTP error, or zero spots returned).
- `Services/amapPlaces.js` — real place lookup against Amap's Web Service "place text search" API (`searchPlaces(query, city)`), used by `/trip/intake`'s accommodation-confirm stage. Requires `AMAP_WEB_SERVICE_KEY` — falls back to a single unverified candidate if unset or if the call fails.
- `Validation/` — plain-function request-body validators (`login.js`, `register.js`, `resetPassword.js`, `isEmpty.js`).

**Conventions:**
- Route handlers use `.then()/.catch()` (not async/await) throughout `APIs/auth.js` and `APIs/trip.js`.
- DB model fields are PascalCase (`FirstName`, `Email`, `ResetToken`), matching DS-Service's convention — keep new fields consistent with this casing.
- User-facing auth routes issue tokens via `generateAccessToken(user, 'auth' | 'refresh' | 'deepseek')` in `Config/jwtgenerator.js`. The `'deepseek'` usage is what signs the `token` field DS-Service expects (60s expiry, secret `DEEPSEEK_JWT_SECRET` — must match DS-Service's copy of the same secret).
- Calls into DS-Service go through `axios` with the base URL `process.env.DS_SERVICE_BASEURL`; see `APIs/dsservice.js` for the current pattern (mint a `'deepseek'` token, attach it as `token` in the JSON body — not a header — then POST).

**Env vars** (`Node/.env`): `PORT`, `MONGODB_URL`, `ACCESSSECRETE`, `REFRESHSECRETE`, `RESETSECRET`, `EMAIL_VERIFY_SECRET` (signs the 24h email-verification JWT minted on register, see `APIs/auth.js`), `DEEPSEEK_JWT_SECRET`, `GD_MAP_JWT_SECRET`, `AMAP_WEB_SERVICE_KEY` (Amap Web service key for `Services/amapPlaces.js` — distinct from `GD_MAP_JWT_SECRET` and from the JS API key `useAmap.js` loads client-side), `DS_SERVICE_BASEURL`, `EMAIL`/`EMAILPASS` (nodemailer SendinBlue credentials used by `Emails/verifyEmail.js`, `welcomeEmail.js`, `forgotPasswordEmail.js`).

## `react-frontend/` — React SPA

Tech: React 19, Redux Toolkit + Redux Thunk, React Router v6, MUI + Emotion, axios.

**Commands** (run from `TBS/react-frontend/`):
- `npm start` — dev server (`react-scripts start`), proxies API calls to `http://localhost:6666` (see `"proxy"` in `package.json` — i.e. the `Node/` backend above, not DS-Service directly)
- `npm run build` — production build
- `npm test` — CRA/Jest test runner (`react-scripts test`)

**Structure:** standard Create React App layout — `src/actions`, `src/reducers`, `src/components`, `src/hooks`, `src/utils`, `src/store.js` (Redux store setup), `src/App.js`.

**Conventions:** the frontend never talks to DS-Service directly — it goes through the `Node/` backend (`/dsservice/*`, `/trip/*` routes), which in turn calls DS-Service. If you're adding a UI feature that needs DS-Service data, the new/changed logic belongs in `Node/APIs/dsservice.js` (or a new route module) first, following DS-Service's contract, then wired up to the frontend through the existing proxy.

**Design for a future mobile app.** There's no mobile app in development right now, but one is planned, so keep that in mind on every UI decision here — even though today's target is web only. Concretely: avoid layout/interaction patterns that only make sense on a wide desktop viewport and would need a full rework for a native-sized screen (e.g. fixed pixel widths instead of relative/responsive sizing, hover-only interactions with no tap equivalent, multi-column layouts with no real mobile fallback). This isn't a mandate to build responsive/mobile-first *now* — it's a bias to apply when there's a reasonably low-cost choice between a web-only pattern and one that would translate more easily later.

### Bugs

Actual defects — existing behavior is wrong, not just missing. Prioritized ahead of the feature backlog below.

- **Vague arrival/departure-point answers can fuzzy-match to an unrelated real place.** During intake, answering the "where will you be departing from" question with something like "same airport" (instead of repeating the airport's full name) got resolved via Amap's place-text-search to "SAME SIAM热啊东南亚餐厅(中关村领展广场店)" — a Thai restaurant whose name happens to start with "SAME" — rather than being recognized as referring back to the already-given arrival point, or re-prompting for a clearer answer. Surfaced while testing the Itinerary map's route-drawing feature (arrival/departure resolution, `Services/amapPlaces.js` / `APIs/trip.js`'s `resolvePlacePoint()`); not fixed as part of that work.

Needs either server-side i18n on the reply templates (or, for spot data, sourcing it bilingually / a translation pass over `DestinationSpot`) or an LLM-based translation pass; a distinct, larger effort from the UI switcher.
- **Get native-speaker/professional localization review of all Chinese UI copy before launch.** The initial `zh/translation.json` pass (and any future one, including the two items above) was AI-translated and then AI-revised for naturalness — competent, but not a substitute for native-speaker sign-off, especially since **China is this product's first launch market, not an afterthought**. Past naturalness issues already caught and fixed once (e.g. "冒险" reading as extreme-sports tone in the hero headline, "行程摘要" reading as a bureaucratic document term, budget-tier labels not matching real Chinese OTA conventions) are the kind of thing a native reviewer catches immediately and an AI pass can miss again next time. Get this review before any Chinese copy — current or future — ships to real users.
- **Per-day colored *and numbered* map markers on the Itinerary page.** The AMap panel (`components/itinerary/Itinerary.js`) currently renders every spot marker identically — `spotsToMarkers()` builds each marker with a `title`/`content`/`position` but nothing distinguishing which day it belongs to or what order it's visited in that day, and `updateMarkers()` creates every `AMap.Marker` with AMap's plain default styling (no custom icon/color at all). Needs two things together: (1) a per-day color — assign each `DayNumber` a distinct color from a fixed palette (needs to support up to 14 days, the max trip duration — see `itineraryPlanner.js`), so all of a given day's spots are visually distinguishable from other days at a glance; (2) a visit-order number within that day (1, 2, 3, ... restarting each day) so a traveler can tell not just which day a spot belongs to but the sequence they're meant to visit it in, directly on the map. Both carry through `spotsToMarkers()`'s output into `AMap.Marker`'s `icon`/`content` option (AMap supports fully custom marker icons/content, not just the default pin) as one combined color+number badge per marker.
- **Add a `GoodToKnow` field per spot, for pre-visit awareness tips.** `DestinationSpot` has no field for practical heads-up information — reservation requirements, typical crowding, weather/gear prep, cash-only, dress code, etc. — distinct from `Fees.Notes` (pricing-specific caveats only) and `BestTimeToVisitInDay`/`BestTimeToVisitInYear` (timing, not preparation). Needs a `GoodToKnow` field added to DS-Service's sourcing prompt (`DESTINATION_SPOT_QUERY`) and `DestinationSpot` schema — free text, not a fixed vocabulary like `Category`, since the content varies too much for a controlled enum and nothing downstream needs to bucket by it — passed through on TBS's side (`spotSourcing.js`'s reshape, `DB_Trip.js`'s `SpotSchema`, same pattern as `Category`), and, unlike `Category` (purely internal to `itineraryPlanner.js`), actually displayed on each spot card on the Itinerary page (`components/itinerary/Itinerary.js`), since the whole point is helping the traveler prepare before they go. Like `Rating`/`Category`, this is LLM-generated and can occasionally be generic or wrong (e.g. claiming a reservation is required when it isn't) — not a blocker, but the UI should frame it as a tip, not a guaranteed fact. Falls under the backend-i18n item above once translation is in scope, same as the rest of a spot's LLM-sourced text.
- **Network-reachability-based provider routing — confirmed to affect the map widget itself, not just POI search quality.** Surfaced while testing the Amap place lookup used for the has-a-place accommodation flow: Amap's POI data/keyword matching is unreliable outside mainland China (English-language searches for well-known hotels in Paris/Tokyo returned irrelevant results even with correct city scoping). Confirmed in later testing that this is more than a search-quality issue: Amap's *base map tiles* themselves don't render for non-China destinations at all — the accommodation-candidate map and the Itinerary page's map (`components/itinerary/Itinerary.js`) both show a blank grid with only the markers visible (no roads, no labels, no imagery) for e.g. Ghent or Prague, while the same map instance renders full detail instantly for a China location (confirmed by the geolocation-recenter bug above accidentally landing the viewport in Kunming). Consistent across multiple destinations and load waits well beyond normal tile-load latency, so this reads as a genuine coverage gap in Amap's tiles outside China, not a slow-render issue. The routing needed here is two separate axes, not one "China vs. not" switch:
  - **User's network/region is the reachability gate, not a quality preference.** Google's services (Maps included) are blocked at the network level inside mainland China, so a China-network user planning a *non-China* trip still can't be routed to Google Maps — it simply won't load for them, regardless of match quality. Likewise ChatGPT/OpenAI's API is generally unreachable from mainland China. So:
    - **China network** → Amap (+ DS-Service `ds: 'deepseek'`) for **every** destination, for now — not because Amap is a good fit for e.g. a Tokyo search, but because it's the only reachable option. This is an accepted limitation, not a bug, until there's a real fix for the geofencing (e.g. a server-side proxy that calls Google Places from outside China on the user's behalf, so the client never talks to Google directly — worth designing later, not part of this item).
    - **Non-China network** → both Amap and Google Maps are reachable, so **destination-based** routing can apply within this group: Amap for China destinations (best data there), a new `Services/googlePlaces.js` (not yet built) + DS-Service `ds: 'chatgpt'` for non-China destinations (already scaffolded as a `501` stub in `POST /datasourcing/sourcespots` — see DS-Service's `CLAUDE.md` — but not yet implemented).
  - **Check Amap's own "World Map" (世界地图) feature before building a second map provider.** Amap JS API 2.0 has an official overseas coverage mode — `showOversea: true` at map init, claiming 200+ countries/regions with "detailed road data and POI" outside China — which, if it actually delivers usable quality for e.g. Ghent/Prague, would fix this with **zero new integration**: same SDK, same key architecture (`REACT_APP_AMAP_KEY`/`REACT_APP_AMAP_SECURITY_JS_CODE`/`AMAP_WEB_SERVICE_KEY` already in place), reachable from China same as today — potentially closing *both* the non-China-network and the harder China-network+non-China-destination case at once, without a second map provider or the server-side-proxy workaround below. **Do this check first** — it changes the shape of everything below if it works.
    - **Application process:** gated behind a separate commercial approval, not a self-serve flag — requires filing a work-order ticket through Amap's developer console requesting "商务咨询" (business consultation). Needs whoever holds TBS's Amap developer account to actually file it; not something that can be done without that access.
    - **Pricing:** not published anywhere for World Map specifically — only available via that same sales conversation. For context, Amap's general commercial API "Technical Service License" (likely a prerequisite tier, separate from World Map itself) runs ¥50,000/year (Basic) to ¥100,000/year (Premium) — TBS's current Amap keys look like the free/dev tier per the env var docs above, so this would likely mean a paid-tier move at minimum, not just a feature unlock.
    - **Positioning:** a 2025 Amap press release upgrading World Map (300M+ POI, multi-modal navigation) explicitly lists "online travel platforms" as a target customer segment alongside logistics/delivery/ride-hailing — directly relevant to TBS, and a signal it's an actively maintained enterprise product, not an afterthought, but priced/gated accordingly.
    - Sources: [World Map guide](https://lbs.amap.com/api/javascript-api-v2/guide/map/world-map), [World Map solution page](https://lbs.amap.com/solution/abroad), [Amap service/pricing page](https://lbs.amap.com/upgrade), [Amap World Map upgrade press release](https://www.prnewswire.com/news-releases/amap-platform-upgrades-world-map-service-with-multi-modal-navigation-and-300m-poi-302819384.html), [Zhihu discussion of Amap/Tencent/Baidu commercial licensing fees](https://www.zhihu.com/question/484885366).
  - **If World Map isn't viable (denied, too costly, or overseas quality turns out poor in testing), fall back to routing the map widget itself, not just the search API behind it.** For non-China-network users viewing a non-China destination, swap the actual map instance — a new `useGoogleMap` hook alongside the existing `useAmap` (`hooks/useAmap.js`), with `Itinerary.js` and the accommodation-candidate map choosing between them by the same reachability+destination logic, over a shared provider-agnostic marker shape so both map components don't need separate rewrites. For China-network users viewing a non-China destination, there's no equivalent swap available (Google is unreachable), so this stays the accepted limitation above until the geofencing workaround exists.
  - **Cheap interim mitigation, worth doing regardless of which fix above lands:** detect the no-tiles case and show something more honest than a blank grid (e.g. a "map preview unavailable for this destination" notice with the marker list still usable), rather than a map that just looks broken.
  - **Query-language translation follows whichever provider is active, not the user's own language.** Translating the query to Chinese is what actually fixed Amap's match quality in testing — that holds whenever Amap is in use, whether it was chosen because the destination is in China or because the user's network left no other option. No translation is expected to be needed for Google Maps queries (handles multi-language input more gracefully).
  - **UI language and LLM-backend selection are a separate, user-scoped concern**, independent of the above: default UI language from IP region (China IP → Chinese default, overridable via the language switcher — `react-i18next` + `components/layout/LanguageSwitcher.js` now built, currently defaulting to browser language rather than true IP-region detection), and LLM backend follows the same network-reachability gate as the maps provider (China network → Deepseek, regardless of destination).
  - Scope for the eventual PR: land the network-based reachability gate and the destination-based refinement within the non-China group. The non-China Google Maps/ChatGPT build-out and the China-network geofencing workaround are both separate follow-ups, not part of this either.
- **User feedback on spots and itineraries.** A simple rating mechanism — after visiting a spot, and after completing a trip — for the traveler to rate their real experience. Purpose: today's `Rating` field on every spot is entirely an LLM guess (see `DS-Service/CLAUDE.md`'s "How Spot Sourcing Works"); real user ratings, accumulated across the user base, are a first-party, fully-owned data source that could eventually supplement or replace the LLM-guessed rating with something grounded in actual visitor experience. Needs: a new TBS-side rating endpoint/UI (likely on the Itinerary page or a post-trip prompt), a place to store per-user per-spot/per-trip ratings (a new Mongoose collection, since `DestinationSpot` lives in DS-Service's database, not TBS's — the aggregation/rollup of user ratings back into DS-Service's spot data is a separate design question, not just a UI addition), and a decision on how (or whether) aggregated user ratings get blended with or replace the LLM's `Rating` value on each `DestinationSpot`.
- **Offer similar-hotel suggestions when the traveler has a place "in mind" but hasn't booked it.** `STAGES.ACCOMMODATION_CHOICE` (`APIs/trip.js`) asks one bundled yes/no question — "do you already have a place booked or in mind?" — and treats a "yes" identically either way: `searchAndPresent()` looks up the named place and only ever asks the traveler to confirm that exact match (`STAGES.ACCOMMODATION_CONFIRM`). That's the right flow for an already-booked place, but if the traveler only has one *in mind* (not booked), they'd likely also want to see similar alternatives — the same kind of listing `suggestAccommodations()` already produces for the no-place path — rather than a single confirm-or-search-again loop. Needs distinguishing the two cases at the `ACCOMMODATION_CHOICE` stage (a third yes/no-style option, or a follow-up question) and, for the "in mind" case, extending the confirm flow to also offer nearby/similar options. Deliberately not part of the current accommodation-suggestion format work — logged as its own future item.
- **After accommodation is settled, help find flights/train tickets — but only if the traveler doesn't already have their own transportation sorted.** Continues the same post-generation conversation as the now-built accommodation-settling flow (`POST /trip/refine`'s `REFINE_STAGES.PICK_ACCOMMODATION` → `EDITING` transition), one step further: once accommodation is settled, check whether the traveler already has a flight or train booked for their `arrivalPoint`/`departurePoint`. If they say they're driving or otherwise using their own transportation, skip this entirely — leave it blank, no search needed. Otherwise, don't ask about it any earlier in the flow (during intake or itinerary-review) — set it aside and come back to it only as the next step after accommodation, then help find the cheapest available ticket for the traveler's preferred travel dates. Needs a flight/train ticket-search integration (provider not yet decided) — the persistent Itinerary-page chatbot this depends on already exists, so this item is otherwise unblocked.
- **Caching layer for volatile external lookups (e.g. Redis).** Decided against storing a raw price field on the `Accommodation` sub-document (`DB_Trip.js`) since pricing is date/availability-dependent and goes stale almost immediately — it should be fetched live at suggestion/generation time, not persisted in Mongo. That means repeated fetches to `Services/amapPlaces.js` (and its future `googlePlaces.js` sibling) are expected by design, so a caching layer with a short TTL is needed in front of these lookups to avoid hammering the external API on every near-duplicate query. See DS-Service's `CLAUDE.md` for the matching need on its side (LLM-sourcing calls and any future live price fetches).
- **End-to-end test coverage.** Neither `Node/` nor `react-frontend/` has real tests today — `Node/package.json` defines no test script at all, and `react-frontend/package.json`'s `npm test` is CRA's default (`react-scripts test`) with no test files beyond the untouched boilerplate `App.test.js`. Add e2e coverage for the trip-intake flow (stage machine + accommodation confirm/suggest branches) as a starting point — this session's verification of the lodging flow relied entirely on ad hoc manual simulation scripts, which don't persist as regression protection.
- **Build a profile management page.** No profile page exists today — `Navbar.js`'s account dropdown already has "My Profile" and "Settings" items (`t('nav.myProfile')`/`t('nav.settings')`), but both are inert `div`s with no `onClick`/route behind them. Must-have features: (1) **user info, modifiable** — basic identity fields (`FirstName`/`LastName`/`Phone`, `DB_Models/DB_User.js`) are already fetchable via the existing `GET /auth/current` (`Node/APIs/auth.js`, already called by `getProfileInfo()` in `actions/authAction.js`), but there's no update endpoint — needs a new `PUT`/`PATCH /auth/profile`-style route plus the corresponding form UI; (2) **past trip history** and (3) **pending/upcoming trips** — `DB_User.js` already has an unused `TripHistory: [{ TripID: ref Trips }]` schema field (never populated or read anywhere in the codebase — `POST /trip` today only creates the `Trips` document itself, doesn't push its id back onto the owning user), and there's no "list trips for the logged-in user" endpoint at all (`GET /trip/:id` only fetches a single trip by id) — needs both the backend list endpoint and actually wiring `TripHistory` on save. Splitting past vs. upcoming needs a real trip start date to compare against, which doesn't exist yet either: `DaySchema`'s `Date` field is always saved as `null` (see `itineraryPlanner.js`'s `arrangeIntoDays()` and `fallbackItinerary.js`, both hardcode `Date: null`), and `DB_Trip.js`'s only other date field is `CreatedAt` (when the trip was *saved*, not when it's *for*) — likely needs a new top-level `StartDate`/`EndDate` (or similar) on `DB_Trip.js`, asked during intake or left editable on this new page. UI design can reference Wanderlog, same as the Itinerary-page chatbot's own design did.
